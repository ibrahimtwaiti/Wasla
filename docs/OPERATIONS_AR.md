# دليل النشر والتشغيل والتراجع

## حالة التسليم

الإنتاج منشور على Vercel ويستخدم Neon PostgreSQL في Frankfurt. المعاينة في فرع قاعدة مستقل. حساب المدير مفعّل. راجع V1_CLOSEOUT_AR.md للحالة الحالية والبوابات غير المغلقة؛ التعليمات التالية الخاصة بـ Docker تخص التشغيل البديل المحلي فقط.

## البيئة

الإنتاج: FastAPI على Vercel وNeon PostgreSQL؛ لا يستخدم SQLite أو قرص Vercel المؤقت للبيانات. التشغيل البديل: Python 3.12+ وخادم Linux بقرص دائم وTLS reverse proxy. المتغيرات في `.env.example`. التطبيق لا يقرأ .env تلقائيًا في تشغيل Python المباشر؛ صدّر القيم أو استخدم docker compose.

- `WASLA_DB`: مسار دائم لقاعدة البيانات، مشترك بين web وworker.
- `WASLA_ORIGIN`: أصل الموقع الكامل دون slash أخير؛ مثال `https://app.example.com`.
- `WASLA_ENV=production`: مطلوب خارج البيئة المحلية؛ يفرض HTTPS origin وSecure cookies وHSTS.
- `META_APP_SECRET`, `META_VERIFY_TOKEN`: أسرار الربط على الخادم فقط؛ إن لم تضبط تبقى واجهة الاستقبال معطلة.
- `META_GRAPH_VERSION`: محجوز للمرسل المستقبلي وغير مستخدم في V1.

## أول تشغيل

1. تثبيت الاعتماديات وتهيئة DB بأوامر README.
2. تشغيل `python -m wasla.cli bootstrap` مرة واحدة، وكتابة بريد المدير وكلمة مرور طويلة تفاعليًا.
3. تشغيل web وعامل واحد مع المسار نفسه، دون نشر مجلد data أو `/api` عبر cache.
4. ضبط reverse proxy بحد جسم طلب 64 KiB، TLS وإغلاق الوصول المباشر للمنفذ. إبقاء `--no-proxy-headers` أو مراجعة قائمة trusted proxies صراحة؛ لا تثق في X-Forwarded-For من الإنترنت. rate limit الحالي يعتمد عنوان اتصال الخادم وقد يجمع المستخدمين خلف proxy واحد؛ أضف محدد معدل موثوق على الحافة قبل الجمهور.
5. دخول المدير وإنشاء شركة وفريق، ثم طلب اصطناعي والتحقق من الطلب والمشروع.
6. وافق المالك على القرارات A–H والسوق السعودي والاحتفاظ وضوابط الإدارة دون MFA. نصوص الخصوصية والشروط منشورة كإشعارات تشغيلية، لكنها لا تغني عن إثبات تسجيل الجهة والمراجعة القانونية. يبقى الاعتماد مطلوبًا قبل استقبال بيانات جمهور حقيقية أو إغلاق V1 رسميًا؛ لا يُعد التأجيل قبولًا للمخاطر. استبعد المالك MFA من متطلبات V1 مع قبول المخاطر؛ راجع تنفيذ الجلسات والحد الأدنى للصلاحيات وبيانات الجهة القانونية قبل الاستخدام التجاري.

## إعداد استقبال واتساب (لا إرسال)

1. حساب Meta مخول وتطبيق وPhone Number ID وصلاحيات وأسرار مملوكة للمشروع.
2. مدير الشركة يسجل Phone Number ID في القنوات. التسجيل لا يُثبت الاتصال.
3. اضبط الأسرار وURL `/api/webhooks/whatsapp` وأكمل challenge بالـ verify token.
4. تأكد من تشغيل العامل ومن تسليم رسالة نصية من رقم اختبار مخول. راقب الرسالة في صندوق الشركة والحدث processed.
5. اختبر توقيعًا خاطئًا وتكرار الحدث ورسالة جديدة لمحادثة مغلقة ورقم قناة مجهول.
6. لا تُعلن اكتمال واتساب: الإرسال والتسليم والقوالب والمرفقات وقياس صحة القناة ليست منفذة هنا. لا رسوم أو حدود مزود مثبتة في الشفرة.

الأحداث الفاشلة تُحاول خمس مرات ثم dead؛ لوحة صحة التشغيل تعرض المعرف والمحاولات فقط. عالج سبب الفشل ثم أعد المعالجة، ولا تعدل payload من المتصفح. لا يسجل النظام exception كاملًا لتجنب تسريب محتوى أو أسرار؛ التحقيق المفصل للمشغل المخول على الخادم.

## النسخ والاستعادة

```bash
python -m wasla.cli backup /secure-backup/wasla-2026-11-12.sqlite3
```

النسخة تنتج ملف SQLite متسقًا؛ **الأداة لا تشفر النسخة ولا ترفعها ولا تجدولها**. يلزم مشغل يجدول نسخة يومية ويشفرها بأداة معتمدة ويرفعها خارج الخادم ويختبر استعادتها. أهداف الوثيقة RPO≤24h وRTO≤4h أهداف تجارية لم تُقَس في بيئة إنتاج.

الاستعادة: أوقف web وworker، احتفظ بنسخة من القاعدة الحالية بما فيها WAL/SHM، تحقق من النسخة عبر `PRAGMA integrity_check`، استعدها إلى مسار جديد واضبط WASLA_DB، شغّل اختبارًا معزولًا ثم افتح الخدمة. لا تستبدل ملف قاعدة مفتوحة. افحص الطلبات والعملاء والعزل وعينات المحادثات بعد الاستعادة.

## التراجع

1. أوقف استقبال تغييرات جديدة، وخذ نسخة احتياطية متسقة.
2. ارجع إلى commit معروف وrequirements الخاصة به.
3. لا ترجع كودًا أقدم مع schema غير متوافقة. V1 يحتوي ترحيلًا أوليًا واحدًا؛ استعادة بيانات جديدة إلى schema قديمة تحتاج خطة migration مستقلة.
4. شغّل health واختبارات قبول بعينة معزولة ثم أعد استقبال الطلبات.
